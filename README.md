## Запуск

1. Убедитесь, что установлен .NET 9 SDK.
2. В корне репозитория выполните:

   dotnet restore
   dotnet build
   dotnet run --project yp.csproj

3. По умолчанию приложение слушает:
   - http://localhost:5256
   - https://localhost:7149

4. Swagger UI доступен по адресу: http://localhost:5256/swagger (или https://localhost:7149/swagger)

## Запуск тестов

Юнит-тесты находятся в отдельном проекте `EventService.Tests` (xUnit).

Запустить все тесты:

   dotnet test EventService.Tests/EventService.Tests.csproj

Или, находясь в корне репозитория со сборкой (solution), запустить тесты для всех проектов сразу:

   dotnet test

Тесты покрывают сервисы `EventService` и `BookingService`: CRUD, фильтрацию и пагинацию событий, валидацию DTO, резервирование и освобождение мест, статусы бронирований и защиту от овербукинга при конкурентных запросах.

## Endpoints

### События

- GET /events — получить список событий (с фильтрацией и пагинацией, см. ниже)
- GET /events/{id} — получить событие по id
- POST /events — создать событие
- PUT /events/{id} — обновить событие
- DELETE /events/{id} — удалить событие

### Бронирования

- POST /events/{id}/book — забронировать место на событие (создать бронь)
- GET /bookings/{id} — получить информацию о бронировании по id
- POST /bookings/{id}/reject — отклонить ожидающую обработки бронь и освободить место

### Модель события

Помимо основных свойств, событие содержит поля вместимости:

| Поле | Тип | Описание |
|------|-----|----------|
| `totalSeats` | integer | Общее количество мест. Передаётся при создании события и должно быть больше нуля. |
| `availableSeats` | integer | Количество ещё не занятых мест. Устанавливается равным `totalSeats` при создании, уменьшается при бронировании и возвращается при отклонении брони. |

`availableSeats` является состоянием сервера и возвращается в ответах `GET /events` и `GET /events/{id}`; клиент не должен передавать его при создании события.

Пример создания события на три места:

```http
POST /events
Content-Type: application/json

{
  "title": "Конференция по продажам",
  "description": "Ежегодная конференция",
  "startAt": "2026-05-10T10:00:00Z",
  "endAt": "2026-05-10T18:00:00Z",
  "totalSeats": 3
}
```

#### Модель Booking

Бронь имеет следующую структуру:

```json
{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "eventId": "4fa85f64-5717-4562-b3fc-2c963f66afa7",
  "status": "Pending",
  "createdAt": "2026-05-10T10:00:00",
  "processedAt": null
}
```

| Поле | Тип | Описание |
|------|-----|---------|
| `id` | UUID | Уникальный идентификатор брони |
| `eventId` | UUID | ID события, на которое создана бронь |
| `status` | BookingStatus | Текущий статус брони (см. ниже) |
| `createdAt` | DateTime | Время создания брони (UTC) |
| `processedAt` | DateTime? | Время обработки брони (UTC), устанавливается только при переходе в статус `Confirmed` или `Rejected` |

#### Статусы брони (BookingStatus)

| Статус | Описание |
|--------|---------|
| `Pending` | Бронь создана и ожидает обработки. В этом статусе остаётся до момента, пока фоновый сервис её не обработает. |
| `Confirmed` | Бронь подтверждена. Означает, что внешняя система приняла запрос на бронирование. |
| `Rejected` | Бронь отклонена фоновым сервисом: событие было удалено до обработки либо при обработке возникла ошибка. Если событие всё ещё существует, при ошибке зарезервированное место возвращается через `ReleaseSeats`. |

### Описание эндпоинтов событий

#### POST /events/{id}/book — Создание брони

**Запрос:**
```
POST /events/{eventId}/book
```

**Ответ (HTTP 202 Accepted):**
```json
{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "eventId": "4fa85f64-5717-4562-b3fc-2c963f66afa7",
  "status": "Pending",
  "createdAt": "2026-05-10T10:00:00",
  "processedAt": null
}
```

Сервис возвращает статус **202 Accepted** вместе с заголовком `Location`, указывающим, где можно получить информацию о созданной брони:
```
Location: /bookings/{id}
```

Бронь создаётся в статусе `Pending` и автоматически обрабатывается фоновым сервисом.

**Возможные ошибки:**
- **404 Not Found** — событие с указанным `id` не найдено
- **409 Conflict** — для события не осталось свободных мест

#### GET /bookings/{id} — Получение информации о брони

**Запрос:**
```
GET /bookings/{id}
```

**Ответ (HTTP 200 OK):**
```json
{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "eventId": "4fa85f64-5717-4562-b3fc-2c963f66afa7",
  "status": "Confirmed",
  "createdAt": "2026-05-10T10:00:00",
  "processedAt": "2026-05-10T10:00:02"
}
```

**Возможные ошибки:**
- **404 Not Found** — бронь с указанным `id` не найдена

#### POST /bookings/{id}/reject — Отклонение брони

Отклоняет бронь в статусе `Pending`. Если событие существует, место сразу возвращается в `AvailableSeats` через `ReleaseSeats`, поэтому его можно забронировать повторно. Повторное отклонение или отклонение уже подтверждённой брони возвращает **409 Conflict**.

### GET /events — параметры фильтрации и пагинации

Все параметры передаются через query-строку и являются опциональными. Если параметр не указан, соответствующий фильтр не применяется. Все фильтры комбинируются по логическому И.

| Параметр    | Тип      | По умолчанию | Описание |
|-------------|----------|--------------|----------|
| `title`     | string   | —            | Поиск по названию события, регистронезависимый, частичное совпадение |
| `from`      | DateTime | —            | Только события, которые начинаются не раньше указанной даты (`StartAt >= from`) |
| `to`        | DateTime | —            | Только события, которые заканчиваются не позже указанной даты (`EndAt <= to`) |
| `page`      | int      | 1            | Номер страницы (нумерация с 1) |
| `pageSize`  | int      | 10           | Количество событий на странице |

Пример запроса:

   GET /events?title=конференция&from=2026-05-01T00:00:00&to=2026-05-31T23:59:59&page=1&pageSize=10

Ответ возвращается в формате `PaginatedResult`:

```json
{
  "items": [
    {
      "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
      "title": "Конференция по продажам",
      "description": "Ежегодная конференция",
      "startAt": "2026-05-10T10:00:00",
      "endAt": "2026-05-10T18:00:00"
    }
  ],
  "totalCount": 1,
  "page": 1,
  "pageSize": 10
}
```

- `items` — события на текущей странице (после применения всех фильтров);
- `totalCount` — общее количество событий, подходящих под фильтры (без учёта пагинации);
- `page` — номер возвращённой страницы;
- `pageSize` — размер страницы.

## Фоновая обработка бронирований

### Общее описание

Приложение использует встроенный `BackgroundService` (`BookingProcessingService`) для асинхронной обработки бронирований. Сервис работает в отдельном потоке выполнения и не блокирует основное приложение.

### Логика обработки

1. **Опрос очереди** (polling): Фоновый сервис каждые 5 секунд проверяет наличие бронирований в статусе `Pending`.

2. **Имитация внешнего запроса**: Для каждого найденного `Pending` бронирования сервис:
   - Логирует начало обработки
   - Ждёт 2 секунды (имитирует обращение к внешней системе)
   - Переводит статус в `Confirmed`, если событие существует и обработка завершилась без ошибки
   - Обновляет время обработки (`ProcessedAt`)
   - Логирует результат обработки

3. **Обработка ошибок**: При возникновении исключения во время обработки сервис отклоняет бронь, возвращает место через `ReleaseSeats`, если событие ещё существует, логирует ошибку и продолжает работу. Если событие уже удалено, бронь также отклоняется; возвращать место некуда, поскольку объект события отсутствует в хранилище.

4. **Корректное завершение**: При остановке приложения сервис правильно завершает работу (поддерживает `CancellationToken`).

### Параметры конфигурации

| Параметр | Значение | Описание |
|----------|----------|---------|
| `_pollingInterval` | 5 сек | Интервал между проверками новых бронирований в очереди |
| `_simulatedExternalDelay` | 2 сек | Имитируемая задержка обращения к внешней системе |

### Синхронизация и защита от овербукинга

Резервирование места и создание брони выполняются внутри одного `lock` в `BookingService`. Поэтому два одновременных запроса не могут одновременно увидеть одно и то же последнее свободное место: один успешно уменьшит `AvailableSeats`, а второй получит `409 Conflict`.

`InMemoryEventStore` защищает операции со списком событий собственным `lock`. Брони хранятся в `ConcurrentDictionary`, что позволяет безопасно читать и обновлять их из HTTP-обработчиков и фонового сервиса. В `BookingProcessingService` используется `SemaphoreSlim(1, 1)`, чтобы смена статуса брони и связанное обновление состояния выполнялись последовательно.

### Пример потока обработки

1. Клиент делает `POST /events/{id}/book` → получает бронь с статусом `Pending`
2. Клиент может сразу же запросить `GET /bookings/{bookingId}` → получит статус `Pending`
3. Фоновый сервис (в течение 5 сек) находит бронь и начинает её обработку
4. После 2 сек задержки статус меняется на `Confirmed` и устанавливается `ProcessedAt`
5. Клиент может затем запросить `GET /bookings/{bookingId}` → получит статус `Confirmed` с временем обработки

## Пример сценария использования

### Сценарий: Бронирование места на конференцию

1. **Получение списка событий:**
   ```
   GET /events?title=конференция&from=2026-05-01T00:00:00&to=2026-05-31T23:59:59&page=1&pageSize=10
   ```
   Ответ:
   ```json
   {
     "items": [
       {
         "id": "4fa85f64-5717-4562-b3fc-2c963f66afa7",
         "title": "Конференция по продажам",
         "description": "Ежегодная конференция",
         "startAt": "2026-05-10T10:00:00",
         "endAt": "2026-05-10T18:00:00"
       }
     ],
     "totalCount": 1,
     "page": 1,
     "pageSize": 10
   }
   ```

2. **Создание брони на конференцию:**
   ```
   POST /events/4fa85f64-5717-4562-b3fc-2c963f66afa7/book
   ```
   Ответ (HTTP 202 Accepted с заголовком Location):
   ```json
   {
     "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
     "eventId": "4fa85f64-5717-4562-b3fc-2c963f66afa7",
     "status": "Pending",
     "createdAt": "2026-05-10T09:00:00"
   }
   ```
   Заголовок:
   ```
   Location: /bookings/3fa85f64-5717-4562-b3fc-2c963f66afa6
   ```

3. **Проверка статуса брони (находя в статусе Pending):**
   ```
   GET /bookings/3fa85f64-5717-4562-b3fc-2c963f66afa6
   ```
   Ответ (сразу после создания):
   ```json
   {
     "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
     "eventId": "4fa85f64-5717-4562-b3fc-2c963f66afa7",
     "status": "Pending",
     "createdAt": "2026-05-10T09:00:00",
     "processedAt": null
   }
   ```

4. **Проверка статуса брони спустя несколько секунд (после обработки фоновым сервисом):**
   ```
   GET /bookings/3fa85f64-5717-4562-b3fc-2c963f66afa6
   ```
   Ответ (после обработки, обычно в течение 7 секунд):
   ```json
   {
     "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
     "eventId": "4fa85f64-5717-4562-b3fc-2c963f66afa7",
     "status": "Confirmed",
     "createdAt": "2026-05-10T09:00:00",
     "processedAt": "2026-05-10T09:00:07"
   }
   ```

### Сценарий: защита от овербукинга

1. Создайте событие с `totalSeats: 3` и сохраните его `id`.
2. Три раза вызовите `POST /events/{id}/book`. Каждый запрос вернёт `202 Accepted`, а `availableSeats` события станет равен `0`.
3. Выполните четвёртый вызов `POST /events/{id}/book`. Сервер вернёт `409 Conflict`:

```json
{
  "type": "https://httpstatuses.io/409",
  "title": "Нет доступных мест",
  "status": 409,
  "detail": "No available seats for this event",
  "instance": "/events/{id}/book"
}
```

4. Через один цикл фоновой обработки (обычно до 7 секунд) запрос `GET /bookings/{bookingId}` для любой из первых трёх броней вернёт статус `Confirmed` и непустое `processedAt`.

## Формат ответа при ошибках

Все ошибки (400, 404, 409, 500) обрабатываются единым middleware и возвращаются в формате, совместимом с Problem Details (RFC 7807), с типом контента `application/problem+json`.

Общая структура ответа:

```json
{
  "type": "https://httpstatuses.io/{status}",
  "title": "Краткое описание ошибки",
  "status": 400,
  "detail": "Подробное сообщение об ошибке",
  "instance": "/events/{id}"
}
```

Для ошибок валидации дополнительно присутствует поле `errors` с детализацией по полям:

```json
{
  "type": "https://httpstatuses.io/400",
  "title": "Ошибка валидации",
  "status": 400,
  "detail": "Один или несколько параметров запроса некорректны.",
  "instance": "/events",
  "errors": {
    "EndAt": ["EndAt должен быть позже StartAt."]
  }
}
```

Используемые статусы:

| Статус | Когда возвращается |
|--------|---------------------|
| 400 Bad Request | Невалидные данные в теле запроса (например, `EndAt` раньше или равен `StartAt`), пустое тело запроса, некорректные параметры фильтрации/пагинации (например, `from > to`) |
| 404 Not Found | Событие с указанным `id` не найдено (при `GET`, `PUT`, `DELETE`) или бронь с указанным `id` не найдена |
| 409 Conflict | Бронь нельзя создать, потому что у события не осталось свободных мест |
| 500 Internal Server Error | Любая непредвиденная ошибка на сервере |
